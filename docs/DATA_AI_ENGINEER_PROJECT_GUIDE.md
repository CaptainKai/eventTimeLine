# Event Timeline Engine：数据与 AI 应用研发岗位项目说明

> 本文为升级前版本。当前实现、量化结果和项目边界请以 `docs/DATA_AI_PROJECT_DESCRIPTION_V2.md` 为准。

## 1. 项目定位

Event Timeline Engine 是一个面向公开新闻与事件情报的多源数据智能系统。它将 GDELT、金十数据、NewsMinimalist、RSS 等异构信息统一接入，经过清洗、去重、结构化事件抽取、实体与动作归一化，形成以 `proto_events` 为事实节点、以 `relationship_summaries` 为主题聚合层、以 `atomic_event_relationships` 为事件关系边的时序知识图谱，并通过 API 和 Dashboard 提供查询、追溯与分析能力。

从数据工程视角看，它不是单纯的“LLM 新闻摘要应用”，而是一条完整的数据生产链路：

```text
多源异构数据
  -> 统一接入与幂等落库
  -> 解析与质量校验
  -> 实体/动作标准化
  -> 原子事实建模
  -> 主题聚合与关系构建
  -> API / Dashboard / 分析应用
```

项目的核心价值是把非结构化新闻转化为可查询、可关联、可回放、可追溯的结构化事件资产，为后续问答 Agent、异动溯源、自动报告和情报研判提供可信上下文。

## 2. 数据架构解释

### 2.1 数据链路

| 阶段 | 项目实现 | 数据工程含义 |
| --- | --- | --- |
| Source | GDELT、Jin10、RSS、NewsMinimalist | 多源异构数据接入 |
| Raw | `news`、来源字段、原文、发布时间 | 保留原始事实与来源凭证 |
| Detail | `proto_events` | 将文章拆为原子事件事实 |
| Standardization | `entity_mapping`、动作标准化、待审核归一化 | 主数据管理与口径治理 |
| Aggregate | `relationship_summaries`、成员关系 | 面向主题和关系的聚合数据层 |
| Serving | REST API、Dashboard、图谱接口 | 数据服务与应用层 |
| Governance | 审核日志、一致性检查、回填重建、任务状态 | 数据质量、可恢复性与可观测性 |

### 2.2 与 ODS/DWD/DWS/ADS 的类比

项目当前没有使用 Hive 数仓，也没有正式采用 ODS/DWD/DWS/ADS 命名，面试时应表述为“具备相似分层思想”，不能说成已经建设了标准离线数仓。

| 数仓层次 | 项目中的对应对象 | 说明 |
| --- | --- | --- |
| ODS | `news`、`raw_events`、来源状态 | 保存来源、原文、发布时间和原始扩展字段，尽量减少业务加工 |
| DWD | `proto_events`、实体映射、动作标准化结果 | 拆分为最细粒度事件事实，完成清洗、去重、标准化和质量标记 |
| DWS | `relationship_summaries`、summary members、原子关系边 | 按主题、时间和实体关系形成可复用的主题数据集 |
| ADS | Dashboard 聚合接口、新闻谱系、关系图接口 | 面向检索、展示、研判和报告的应用数据服务 |

这套映射体现了三项可迁移能力：保留原始层以便回溯、构建稳定事实粒度、将复杂计算前置为可复用主题资产。

### 2.3 事实粒度与维度建模

`proto_events` 可以解释为核心事件事实表，基本粒度是“一篇新闻中拆出的一个原子动作事实”。典型度量或质量字段包括置信度、重要度、时间和解析元数据；典型维度包括来源、时间、实体、地点、动作类型与事件类型。

知识图谱和星型模型并不冲突：

- 星型模型适合稳定指标聚合，如按来源、日期、事件类型统计事件量、解析成功率和重复率。
- 图模型适合多跳关系查询，如某事件的前因后果、共同实体、主题桥接和演化路径。
- 本项目以 PostgreSQL 关系表保存节点和边，兼顾事务、索引、SQL 分析与图语义，不依赖专用图数据库。

### 2.4 增量、幂等与可恢复处理

项目通过唯一键、Upsert、来源处理标记和预检避免重复写入；通过数据库任务队列将实时写入与高成本关系计算解耦；通过 `pending/running/completed/failed` 状态、重试次数、延迟执行时间和失败重置实现任务恢复；通过全量重建、范围回填和 dry-run 支持历史数据修复。

这部分应重点回答“数据重跑是否会重复”“任务失败如何恢复”“实时请求为何不被图计算阻塞”三个问题。

## 3. AI 应用解释

### 3.1 LLM 在系统中的职责

LLM 不是直接生成最终业务结论，而是承担受约束的结构化抽取与归一化任务：

1. 从新闻中拆分原子事件。
2. 提取主体、动作、客体、时间、地点和证据。
3. 对实体名称和动作表达进行标准化。
4. 输出固定 JSON 结构，由代码完成解析、校验、裁剪和持久化。

工程侧提供重试、指数退避、容错 JSON 提取、字段校验、置信度裁剪、原始 Prompt 与响应留存，以及 enhanced/traditional parser 降级路径。其设计原则是“LLM 负责语义理解，代码和数据库负责确定性约束”。

### 3.2 与 RAG 的关系

当前项目已经具备 RAG 的数据底座，但尚未形成完整的向量检索问答链路。

已具备：

- 可检索知识单元：新闻、原子事件、关系 Summary、实体和关系边。
- 元数据过滤条件：时间、来源、实体、动作、事件类型和置信度。
- 多跳上下文：summary 成员、事件边、新闻到事件的谱系。
- 来源追溯：结果可以回到原始新闻和解析记录。

待补齐：

- Embedding 生成、向量索引和混合检索。
- Query Rewrite、召回评估与重排。
- 基于证据的回答生成和引用。
- 离线评测集、Recall@K、MRR、Faithfulness 等指标。

面试时可给出推荐检索策略：先做实体、时间与事件类型过滤，再进行 BM25/向量混合召回；以关系 Summary 扩展相关原子事件；按来源可靠性、时间新鲜度、语义相关度和事件置信度重排；最后携带原文证据生成答案。

### 3.3 与 Data Agent 的关系

项目当前更准确的定位是“Data Agent 的可信数据与工具底座”，而不是已经完整实现自主规划 Agent。

可直接封装为 Skill 的能力包括：

- `search_news`：按时间、来源和关键词检索新闻。
- `get_event_lineage`：追溯新闻、原子事件、主题和关系。
- `query_relationship_graph`：查询某主题内部的事件关系。
- `normalize_entity`：实体标准化和别名对齐。
- `trace_anomaly`：从指标或事件异动回溯来源新闻与关联事实。
- `generate_event_report`：基于时间窗和主题生成带来源的事件报告。

可信 Data Agent 需要在项目现有能力上继续增加：工具 Schema、权限控制、SQL 只读与成本限制、执行前校验、结果引用、审计日志、评测集和人工反馈闭环。

## 4. 数据质量与可信性

项目的可信性不是依靠单次 Prompt，而是由多层约束共同实现：

| 风险 | 当前机制 | 可继续完善 |
| --- | --- | --- |
| 重复采集 | 来源 URL 唯一性、预检、Upsert | 内容指纹与近重复检测 |
| LLM 格式漂移 | JSON 提取、字段校验、失败记录 | JSON Schema constrained decoding |
| 实体别名和歧义 | 实体映射、层级、待审核项 | Golden Set 与实体消歧指标 |
| 关系误判 | 置信度、候选预筛、summary 内构边 | 人工标注集与阈值校准 |
| 中间任务失败 | DB Queue、重试、失败重置 | 死信队列、监控告警、SLA |
| 历史逻辑升级 | 回填、重建、dry-run | 数据版本、任务版本与可重复快照 |
| 结果不可解释 | 原始新闻、解析记录、关系成员 | 回答级引用和证据覆盖率 |

## 6. 面试项目介绍模板

### 6.1 一分钟版本

我做的是一个多源新闻事件智能系统。数据从 GDELT、金十和 RSS 等来源接入后，先以统一模型幂等落库，再通过规则和 LLM 将文章拆成原子事件，完成实体、动作和时间标准化，最后构建主题 Summary 和原子事件关系图，通过 API 支撑时间线、关系追溯和分析看板。这个项目对我最大的锻炼不是调用模型，而是把 AI 输出接入一条可恢复、可审计的数据链路：我设计了原始层、事实层、主题聚合层和应用层的分层结构，用数据库任务队列解耦实时摄入与高成本构边，并通过置信度、审核队列、一致性检查和历史回填保证结果可信。它与数据 Agent 岗位最匹配的地方，是已经沉淀了知识资产、图谱和工具接口；下一步可以直接扩展为带混合检索、SQL Tool、证据引用和评测体系的 Data Agent。

### 6.2 三分钟版本

项目要解决的问题是：多源新闻数据格式不同、内容重复、实体叫法不一致，且一篇文章包含多个动作，直接做全文检索无法回答事件之间的因果、演化和主题关联。

我把系统拆成四层。第一层是采集和原始数据层，各来源通过适配器转换为统一新闻模型，并依靠唯一键、Upsert 和来源处理标记保证增量与幂等。第二层是原子事实层，规则 Parser 和 LLM Parser 将文章拆成主体、动作、客体、时间、地点等结构化事件；模型输出不会直接入库，而是经过 JSON 容错、Schema 校验、置信度处理和实体动作归一化。第三层是关系聚合层，以原子事件为不可变事实，先归属 relationship summary，再由异步 Worker 在 summary 内构建关系边，避免全库两两比较。第四层是服务层，通过 REST API 和 Dashboard 提供检索、图谱下钻和新闻谱系。

工程上的重点是可信和可恢复。实时写入只负责保存事实并投递任务，复杂图计算由数据库队列异步执行；任务有状态、重试次数和失败恢复；算法或口径升级后可以 dry-run、范围回填或全量重建。对于低置信度或未知实体，系统进入待审核队列，而不是让模型结果直接成为权威口径。

如果按数仓语言理解，`news` 类似 ODS，`proto_events` 类似 DWD 原子事实，summary 和关系表类似 DWS 主题聚合，Dashboard/API 类似 ADS。项目没有使用 Hive/Spark/Flink，因此我不会把它包装成大数据平台经验，但分层建模、事实粒度、数据质量、血缘和重跑机制是可迁移的。若数据规模继续增长，我会将采集事件写入 Kafka，Flink 完成实时清洗和维表关联，明细进入湖仓，Spark 承担离线回填与图关系批处理，PostgreSQL 或检索引擎作为 Serving 层。

## 7. 项目亮点 STAR 表达

### 7.1 关系计算复杂度治理

- S：原子事件持续增长，如果全库两两比较，关系构建成本接近平方级增长。
- T：在不牺牲事件可追溯性的前提下控制候选规模，并支持历史数据重建。
- A：设计 Summary-First 两级图；按时间批次做临时候选聚类，先将事件归属到相关 Summary，再只在 Summary 内异步构边；将分配、合并和 detail rebuild 拆为可恢复任务。
- R：将全局关系计算缩小为局部候选计算，实时摄入不再同步等待构边，并获得分阶段回填与失败恢复能力。

### 7.2 LLM 输出可信化

- S：LLM 可能输出非法 JSON、遗漏字段、混淆实体或产生不稳定表达。
- T：让模型输出可以进入数据库并被后续统计与关系计算可靠消费。
- A：限定结构化 JSON 输出；实现容错提取、字段校验、置信度裁剪和重试；保存 Prompt、模型、耗时、状态与错误；增加规则 Parser 降级和待审核归一化流程。
- R：把概率性模型限制在确定性数据契约内，失败可定位、结果可重放、低质量项可人工治理。

### 7.3 多源增量与幂等

- S：多个数据源格式、时间字段和更新方式不同，并发抓取容易产生重复数据和下游重复计算。
- T：建立统一入口，确保同一来源事件重复执行不会破坏一致性。
- A：实现 source adapter 和统一新闻结构；使用来源标识、唯一约束、Upsert、解析状态与 source marker；将通用处理集中到 `processNewsArticle()`。
- R：新数据源只需实现采集和映射即可复用清洗、解析、归一化、入库和图谱链路。

## 8. 面试高频追问与答题要点

### Q1：为什么以原子事件而不是文章作为事实粒度？

一篇文章可能同时包含多个主体和动作。文章粒度会把多个事实压在一个文本块中，无法稳定做指标统计、实体关联和关系推断。原子事件把事实拆为主体—动作—客体及时间地点，使粒度稳定，也让后续去重、归一化和图构建有明确输入。

### Q2：为什么不用 LLM 一次完成所有流程？

模型擅长语义理解，但不适合承担唯一性、事务、权限和口径权威。项目把语义抽取交给 LLM，把校验、标准化优先级、幂等和持久化交给代码与数据库，降低输出漂移对下游的影响。

### Q3：如何保证重跑不产生脏数据？

入口使用业务唯一键和 Upsert；解析和任务表保留状态；关系与成员表使用唯一约束；重建脚本明确清理范围并支持 dry-run；任务失败可重置后继续。进一步可加入 run_id、算法版本和快照版本，实现同一输入同一版本的可重复产出。

### Q4：如何理解项目中的数据血缘？

当前重点是记录级血缘：来源新闻到原子事件，再到 summary 成员和关系边，最终到 API 展示。它能回答“这个结论来自哪篇新闻、经过哪次解析、参与了哪个主题”。字段级 SQL 血缘和任务级 DAG 血缘还没有平台化，若进入数仓环境可接入 OpenLineage/DataHub 一类系统。

### Q5：如果迁移到 Spark/Flink，怎么设计？

Kafka 作为事件总线；Flink 做实时去重、解析状态流转、事件时间窗口和维表关联；湖仓保存 ODS/DWD/DWS 历史数据；Spark 承担离线回填、Embedding 批处理和关系候选计算；Serving 层将高频查询结果同步到 PostgreSQL、Elasticsearch 或向量库。需要重点处理 event time、watermark、exactly-once、维表更新和回放版本。

### Q6：如何评估事件抽取质量？

先建立人工标注 Golden Set，分别评估事件识别、主体/客体、动作、时间和实体链接；使用 Precision、Recall、F1，而不是只看一个“准确率”。对线上再监控 JSON 合法率、空字段率、低置信度率、人工驳回率、同义实体新增率和来源分布漂移。

### Q7：如何做面向 Data Agent 的 RAG？

先解析问题中的实体、指标、时间范围和任务类型；用结构化过滤缩小范围，再做关键词与向量混合召回；利用图关系扩展相邻事件；用时间新鲜度、来源可靠性、语义相似度和置信度重排；生成阶段强制引用新闻和事件 ID。评测同时看召回率、答案正确性、引用覆盖率和 SQL/Tool 执行成功率。

### Q8：如何避免 Agent 生成危险 SQL？

只开放只读账号和白名单视图；先生成逻辑计划，再生成 SQL；做 AST 校验，禁止 DDL/DML 和无条件大扫描；加入行数、时间、扫描量和并发限制；执行前 EXPLAIN 做成本门控；所有请求记录问题、SQL、参数、耗时、结果规模和错误。

### Q9：项目最大的不足是什么？

没有正式使用 Hive/Spark/Flink，RAG 还缺少向量检索和系统化评测，数据血缘以业务记录链路为主而非字段级平台，监控告警与 SLA 也不够完整。优势是已经把最关键的数据契约、事实粒度、质量治理、异步任务和可恢复机制做出来，能清楚说明下一阶段如何平台化。

- 将非结构化文章拆解为原子事件事实，构建实体、动作、时间、地点等标准化模型；通过结构化 Prompt、JSON 校验、重试降级、置信度和人工审核队列约束 LLM 输出。
- 构建 Summary-First 两级时序知识图谱，以原子事件为事实节点，通过主题 Summary 缩小候选范围，并使用数据库任务队列异步完成事件归属、关系构建和失败恢复。
- 建立从原始新闻、解析记录、原子事件到主题与关系边的记录级谱系，提供一致性检查、dry-run、历史回填和全量重建脚本，支持算法与口径升级后的数据治理。
- 通过 REST API 和 Dashboard 提供新闻检索、事件下钻、关系图和谱系追溯能力，为 RAG、异动溯源、自动报告和 Data Agent Tool 化提供数据底座。

## 10. 面试前必须准备的数据

不要使用无法从日志、数据库或测试复现的夸张指标。面试前至少准备以下可验证数据：

1. 当前 `news`、`proto_events`、summary、关系边的记录量。
2. 单次采集成功数、跳过数、失败数和耗时。
3. LLM JSON 成功率、平均耗时、失败重试率和降级率。
4. 抽取 Golden Set 的 Precision、Recall、F1。
5. 重建 1 万条 proto 的耗时、峰值内存和任务失败恢复结果。
6. 典型 SQL 优化前后的 `EXPLAIN ANALYZE`。
7. 一条新闻到原子事件、summary、关系边和 API 展示的完整截图或查询结果。
