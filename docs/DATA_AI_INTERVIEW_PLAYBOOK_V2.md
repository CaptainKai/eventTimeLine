## 2. 一分钟项目介绍

我做的是一个多源新闻事件数据与 AI 平台。系统把 28,376 篇新闻加工为 50,263 个原子事件，并构建了 625,560 条事件关系。数据层按 ODS、DWD、DWS、ADS 思路组织：新闻是原始事实，原子事件是最细事实粒度，关系 Summary 是主题聚合，Query Service 和工作台是应用层。

这次升级的重点是把单体分析应用改造成可演进的数据平台。我增加了 8 个数据契约、5 个 Kafka Topic、Transactional Outbox 和独立 Parser Worker；实现 Spark 离线回填与关系重算代码，以及 Flink 的事件时间、Watermark、去重、迟到处理和小时聚合；在应用层实现 Embedding 检索、关键词降级、6 个查询接口和 5 个可审计 Agent Tool。

前端已经打通主题、语义检索、新闻血缘、图谱和 Agent 调试。Node 测试从 89 增至 108，增长 21.35%；Python 测试从 6 增至 9，增长 50%。DWS 基准 P50 从 752.06ms 降至 1.39ms，提升 541.52 倍，Top 50 结果一致率 100%。我会明确说明 Spark/Flink 尚未完成集群 Runtime 验证，权威路径仍在 PostgreSQL。

## 3. 三分钟项目介绍

项目最初的问题是多源新闻格式不统一、文章粒度太粗、实体口径不一致，而且 LLM 输出具有概率性，不能直接作为可信数据。我的处理方式是先定义事实粒度和治理边界，再引入大数据组件。

第一，数据建模。我把一篇新闻中的一个主体—动作—客体定义为原子事件事实，保留时间、地点、来源、置信度和处理版本。当前有 28,376 篇新闻和 50,263 个原子事件。关系计算采用 Summary-First：先按实体、动作、时间桶缩小候选，再在主题内部构边，目前形成 973 个 Summary 和 625,560 条关系边。

第二，批流架构。我定义了 8 个 JSON Schema 和 5 个 Topic，用稳定 ID 解决跨 PostgreSQL、Kafka、Spark、Flink、Iceberg 的关联问题。写入侧通过 Outbox 保证数据库和消息发布最终一致；Parser Worker 独立消费。Spark 负责历史导出、ODS-DWD、Iceberg 写入和关系重算；Flink 负责事件时间、Watermark、去重、迟到处理和小时指标。当前这些是开发版代码与逻辑测试，生产权威路径还没有切换。

第三，AI 应用。我实现了 Embedding 文本模板、OpenAI-compatible Embedding 请求、PostgreSQL 余弦检索和关键词降级。Query Service 的每个响应都返回版本、生成时间、来源 ID 和血缘 ID。基于它实现了 5 个 Agent Tool，所有参数经过白名单、条数和时间范围校验，并记录 Request ID、耗时、证据和错误。

第四，端到端应用。我新增数据与 AI 工作台，可以从热点主题进入语义检索，选择新闻后查看解析血缘和图谱，也可以直接调试 Agent Tool。真实冒烟中，页面和接口均返回 200，样例链路返回 2 条新闻、1 个原子事件和 20 个图谱节点，Request ID 能关联到 Agent 审计。

结果上，Node 测试从 89 增加到 108，增长 21.35%；Python 测试从 6 增加到 9，增长 50%；历史新闻稳定 ID 覆盖率从 0% 提升到 100%；DWS P50 查询提升 541.52 倍。没有量化的部分我不会夸大：向量表尚未回填，所以没有 Recall@K；没有 Spark/Flink 集群，所以没有吞吐和 Checkpoint 恢复数据。

## 4. 四个核心 STAR 案例

### 4.1 从单体处理升级为批流架构

- **S**：采集、解析和关系计算耦合在主进程，历史重算会影响在线处理。
- **T**：在不立即替换权威链路的前提下，引入可回放、可扩展的数据平台能力。
- **A**：定义稳定 ID 和 Schema；增加 5 个 Topic、Outbox 和 Parser Worker；拆分 Spark 离线与 Flink 实时职责；采用 Shadow Run 和 Feature Flag 迁移策略。
- **R**：形成 10 个 Spark/Flink 源码/配置文件、227 行批流代码，以及 8 张平台表；旧链路保持可用。

### 4.2 把 RAG 从设计变成可运行检索

- **S**：旧系统只有关键词查询和知识图谱，无法进行语义召回。
- **T**：提供可降级、可追溯的语义检索，而不是绑定单一向量数据库。
- **A**：构建分对象 Embedding 文本；调用兼容 Embedding API；保存向量和版本；执行余弦检索；失败时回退关键词；统一返回证据元数据。
- **R**：新增完整语义检索 API 和 UI；但当前向量记录为 0，因此结果质量提升尚未量化，后续用 Recall@K/MRR 评测。

### 4.3 把 Agent 从概念升级为可信 Tool

- **S**：已有查询 API，但 Agent 无法安全复用，也无法审计调用。
- **T**：把数据能力封装为有限、可验证、可追踪的工具集合。
- **A**：实现 5 个 Tool；限制参数、条数和 366 天时间范围；统一证据元数据；记录成功、拒绝和失败；前端按定义动态生成表单。
- **R**：Tool 数量从 0 到 5，HTTP 路由从 0 到 6；真实冒烟验证 Request ID 透传和审计记录落库。

### 4.4 建立可量化的质量底座

- **S**：旧链路依靠业务表和零散测试，跨语言主键、Schema 漂移和新旧链路差异难以验证。
- **T**：让升级可以对账、回放和回归。
- **A**：增加 Golden Set、评测脚本、跨存储对账、统一运行指标、Node/Python 稳定 ID 测试向量和前端纯函数测试。
- **R**：Node 测试 89→108，增加 19 个、增长 21.35%；Python 测试 6→9，增加 3 个、增长 50%；最终 117 项测试全部通过。

## 5. 高频追问与回答

### Q1：你真的使用了 Spark/Flink 吗？

我完成了 PySpark/PyFlink 开发版任务和确定性逻辑测试，包括 Iceberg DDL、事件时间、Watermark、去重、迟到处理、小时聚合、历史回填和关系重算。但当前机器缺少完整 Runtime，没有做集群部署、吞吐和恢复测试，所以我不会说是生产经验。面试时可以直接展示 Job 代码、输入输出契约和测试。

### Q2：为什么 Spark 和 Flink 都要用？

Flink处理持续到达的数据、事件时间、低延迟去重和小时增量指标；Spark处理大范围历史回填、全量质量审计、Embedding 批处理和关系重算。把交互式查询留给 Serving 层，而不是让 Flink“负责实时查询”。

### Q3：如何保证 Kafka 与数据库一致？

业务数据和 Outbox 在同一数据库事务中写入。Publisher 通过状态、重试、锁定时间和幂等事件 ID 发布。Kafka 暂时不可用不会回滚旧主流程，恢复后可以补发。这是最终一致，不冒充分布式强一致。

### Q4：RAG 的检索策略是什么？

先做时间、来源和对象类型过滤，再进行关键词或向量召回；利用 Summary 和图关系扩展上下文；按相关度、来源可靠性、时间新鲜度和事件置信度重排；返回时强制携带来源 ID、版本和血缘。当前已实现向量召回与关键词降级，重排和 Recall@K 评测待补。

### Q5：Agent 如何避免不可信？

Agent 只能调用 5 个白名单 Tool，不能直接执行任意 SQL。参数、条数和时间范围均校验；结果带来源与版本；调用写审计表；错误分为 rejected 和 failed。下一步才是 Planner 和自动报告生成，可信工具层先于自治能力。

### Q6：你量化提升了什么？

我只报告可复现指标：Node 测试增加 19 个，增长 21.35%；Python 测试增加 3 个，增长 50%；DWS P50 查询提升 541.52 倍；稳定 ID 覆盖率 0%→100%；新增 8 个 Schema、5 个 Topic、5 个 Agent Tool、7 个 Query/Agent/Authority 接口、8 张平台表。流式吞吐和模型准确率没有基线，所以不虚构百分比。

### Q7：项目现在最大的缺口？

第一，C01-C03 权威链路尚未切换；第二，Spark/Flink 未做真实集群恢复和性能测试；第三，向量表尚未回填；第四，Golden Set 规模小，没有可对外报告的 F1；第五，没有字段级血缘平台。下一阶段应该优先 Shadow Run 对账，而不是继续堆组件。
