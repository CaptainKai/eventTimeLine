# 开发日志：原子事件关系图谱架构演进与优化 (2026-05-14)

## 1. 任务起因：从“聚类中心”回归“原子关联”

**原始问题**：
旧架构依赖 L3 标准事件 (`canonical_events`) 聚类。其本质是**有损压缩**：多个相似原子事件被强行合并为一个中心节点。这种方式虽然减少了节点数，但导致：
1. **信息丢失**：原子事件间的细微因果链条被抹平。
2. **聚类死板**：一旦聚类错误，后续关系分析全部受损。

**新目标**：
直接以原子事件 (`proto_events`) 为图节点建立关系，实现**基于图关联的动态聚类**。

---

## 2. 演进过程与“弯路”记录

### 阶段 A：全量两两配对 (The O(N²) Trap)
*   **尝试方案**：在 `rebuild-atomic-graph` Phase 2 中，对每个 Summary 内部成员进行全量两两配对。
*   **遇到的瓶颈**：
    *   当 Summary 成员达到 13,000+ 时，配对数激增至 **8900 万对**。
    *   总计算量超过 **58 亿对**，系统彻底卡死。
*   **教训**：在离线回填时，暴力 O(N²) 是不可持续的。

### 阶段 B：采样与剪枝优化
*   **尝试方案**：引入 `MAX_REBUILD_MEMBERS` (1000) 采样，并增加实体 ID 预筛选。
*   **优点**：解决了单点卡死问题。
*   **缺陷**：依然在旧的“两阶段”框架内挣扎，存在大量重复的 DB 查询（Stats 刷新、成员拉取），导致速度仅为 3-8 p/s。

### 阶段 C：流式增量回填 (最终方案)
*   **尝试方案**：模拟系统真实运行，按时间序流式处理原子事件。
*   **核心改进**：
    1. **因果单向性**：强制“过去看不见未来”，新事件只与已有背景比较。
    2. **内存缓存**：引入 `memberCache`，将 DB 往返次数降低了 90% 以上。
    3. **异步/延迟刷新**：回填期间停用统计数据更新，将 CPU 集中于关系发现。

---

## 3. 核心优化技术总结

| 技术点 | 解决的问题 | 性能提升 |
| :--- | :--- | :--- |
| **滑动时间窗口 (30d)** | 限制比较深度，将 O(N) 优化为 O(k) | 极大提升超大节点处理能力 |
| **实体 ID 内存预筛选** | 避免对 80% 无关事件调用昂贵的语义分析逻辑 | CPU 负载降低 70% |
| **同步成员缓存** | 消除重复的成员拉取 SQL | 消除 DB 交互瓶颈 |
| **单向图序** | 确保图结构的逻辑正确性 (因果律) | 减少一半的计算量 |

---

## 4. 架构反思：目前方案是否符合目标？

**结论：基本符合，但仍有进化空间。**

*   **符合度**：
    *   **低损耗**：原子节点被完整保留。
    *   **高性能**：通过流式处理，3 万个节点的处理时间从数小时缩短至分钟级。
    *   **动态性**：关系是随时间流式生成的，符合真实世界事件演化逻辑。

*   **未来优化方向 (L3 的新角色)**：
    现在的 L3 不再是“强行合并”的工具，而应该是**“图社区的抽象”**。
    *   当原子图中的某些区域边密度极大时，自动识别为“事件簇”。
    *   这种基于图拓扑的聚类，比单纯基于语义的聚类更稳健、更具解释力。
