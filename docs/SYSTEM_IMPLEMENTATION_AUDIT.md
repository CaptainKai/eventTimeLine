## 2. 与项目初衷对比

### 2.1 原始初衷

原项目以“事件”为核心：聚合多来源新闻，抽取 actor/action/object 原子事件，形成关系摘要和可浏览图谱，避免把新闻列表误当成事件知识。

**完成情况：基本完成。** 当前数据库中新闻、原子事件和关系摘要能够被查询，主界面能够展示事件链路。仍需重点改善规范事件归并质量；本次集成输出中最近样本的 `canonical_event_id` 多为空，说明“抽取成功”不等于“标准事件沉淀成功”。

### 2.2 数据平台升级初衷

升级目标是用 ODS/DWD/DWS/ADS、稳定 ID、处理版本、数据质量、血缘和批流对账，为 Agent 提供可信上下文；Spark 负责历史回放和离线重算，Flink 负责实时清洗与聚合，PostgreSQL 负责 Serving 和治理。

**完成情况：开发底座完成，权威切换未完成。** B01-B07 和 A01-A09 已形成代码、DDL、任务、接口和测试资产；C01-C03 只具备 Feature Flag、影子查询和审计能力，尚未满足持续对账后切换的验收条件。

### 2.3 Data Agent 初衷

目标不是聊天壳，而是让 Agent 基于可追溯数据调用检索、血缘、指标、溯源和报告工具，并返回版本、来源和降级信息。

**完成情况：Tool 层可用，Agent 层未闭环。** 已有 `search_news`、`get_lineage`、`list_topics`、`trace_anomaly`、`generate_report_context` 五类工具和统一响应元数据；缺 LLM Planner、权限策略、工具调用预算、端到端 Agent Eval，以及从上下文到最终报告的生成与事实校验。

## 4. 测试工程审计

### 4.1 已验证结果

- Node 单元/来源测试：**108/108 通过**。
- Python 数据作业测试：**9/9 通过**。
- 已稳定执行测试合计：**117/117 通过**。
- 数据仓库查询基准：9 次热运行，原始聚合 P50 **752.0593 ms**，DWS P50 **1.3888 ms**，P50 降低 **99.8153%**，加速 **541.517 倍**。
- 聚合正确性：Top50 结果精确一致率 **100%**。
- 稳定标识覆盖：28,376/28,376，**100%**。

这些结果证明“预聚合减少重复计算”和“统一标识支持血缘与幂等”确实产生了可量化价值；它们不能外推为高并发吞吐、生产 SLA 或 Flink 端到端延迟。

### 4.2 集成测试发现

`npm run test:integration` 返回退出码 0，但不能视为集成测试全部通过：

1. `test/integration/l1-l3-flow.test.mjs` 不是 `node:test` 测试，模块加载时直接执行并调用 `process.exit(0)`，导致测试进程提前结束，其他测试套件可能未完整运行。
2. 该脚本捕获异常后仍 `process.exit(0)`，存在失败被报告为成功的假阳性。
3. 脚本向真实 `news`、`proto_events` 和队列表写数据，未清理，污染开发数据库。
4. 部分集成测试在数据库不可用时直接 `return`，会显示通过而非明确 `skip` 或失败。
5. 当前集成测试仍主要验证旧 `raw_events/normalized_events` 模型，未覆盖新 ODS/DWD/DWS/ADS、Outbox、Kafka、Spark、Flink 和 Agent 全链路。

因此测试结论应写成：**117 个隔离测试通过；集成套件存在测试框架和隔离缺陷，不能计入有效通过数。**

## 5. 面试题对应的进一步实践

### Q1：你真的使用了 Spark/Flink 吗？

当前只能严谨回答“完成了可运行作业和本地架构接入，尚未完成生产权威切换”。下一步应保存一次真实 Spark 历史回放和 Flink 持续运行报告，包括输入量、吞吐、checkpoint、backpressure、Lag、失败恢复和资源配置。完成后才能把“写过作业”升级为“运行和治理过作业”。

### Q2：为什么 Spark 和 Flink 都要用？

用同一指标做实践：Spark 重算某日 DWS，Flink 实时累计同一窗口，最终以 stable_id 和窗口键对账。面试时展示相同业务语义在批、流两套执行引擎中的一致性设计，而不是只讲概念。

### Q3：如何保证 Kafka 与数据库一致？

已有 Outbox 是正确起点。进一步注入三类故障：DB 提交后 Publisher 崩溃、Kafka 成功后 offset 未提交、Ingestor 重复消费。用唯一键、幂等更新、重试与 DLQ 证明最终一致，并量化 replay 成功率和恢复时间。

### Q4：RAG 的检索策略是什么？

当前具备关键词降级和向量接口，但向量覆盖为 0。应建立 50-100 条检索 Golden Set，比较 BM25/关键词、vector、hybrid+rerank 的 Recall@K、MRR、P95 和成本；同时让 API 明确返回实际 `retrieval_mode`，避免“请求语义检索、实际关键词检索”不可见。

### Q5：Agent 如何避免不可信？

已有参数白名单、来源 ID、版本和血缘。进一步补充 Tool RBAC、只读账号、调用预算、结果行数上限、Prompt 注入样本、敏感字段脱敏和人工确认节点，再以工具选择正确率、引用完整率和无依据回答率验收。

### Q6：你量化提升了什么？

可以使用已经实测的三组数字：稳定 ID 覆盖从不完整提升到 **100%**；DWS 相对原始聚合 P50 从 **752.0593 ms** 降至 **1.3888 ms**；Top50 一致率 **100%**。不要把 541.517 倍加速描述成所有 API 或生产流量的整体提升。

### Q7：项目最大的缺口是什么？

最可信的回答是：新链路的工程部件已具备，但缺生产级证据闭环，包括 Spark/Flink 长时间运行、批流一致性、真实向量检索、Agent Eval、权限治理和 C01-C03 权威切换。该回答比宣称“全部完成”更符合高级工程判断。

## 6. 推荐改进路线

### 第一阶段：修复测试可信度

1. 将 `l1-l3-flow.test.mjs` 重构为标准 `node:test`，禁止测试模块调用 `process.exit`。
2. 建立 `timeline_test` 数据库或 Testcontainers，所有写测试事务回滚。
3. 给 `npm test` 增加 integration、coverage 和失败阈值，接入 CI。
4. 为新数据平台增加契约、幂等、回放和批流对账测试。

### 第二阶段：形成真实运行证据

1. 启动 Redpanda、MinIO/Iceberg、Spark、Flink，执行固定数据集的完整回放。
2. 记录 Kafka Lag、Spark 吞吐、Flink checkpoint/backpressure、端到端延迟和资源占用。
3. 连续多轮批流对账，要求 count/sum/topN 无不可解释差异。
4. 填充 ADS 后开启影子查询，达到阈值再执行 C01-C03 灰度切换。

### 第三阶段：补齐可信 Agent

1. 完成 embedding 回填和 hybrid retrieval，建立检索评测集。
2. 增加 Planner、工具权限、预算、审计和事实引用校验。
3. 将 `generate_report_context` 扩展为“上下文生成—报告生成—引用校验—人工确认”流程。
4. 建立 Agent 固定回归集并在每次 Prompt、模型和数据版本变更后运行。

## 7. 系统的实际意义

1. **业务意义**：把分散新闻转换成可查询的原子事件和关系摘要，缩短从信息采集到事件研判的路径。
2. **数据工程意义**：用稳定 ID、分层模型、版本、血缘、质量与对账，把 AI 处理结果从一次性输出变成可重放、可核验的数据资产。
3. **性能意义**：实测证明 DWS 预聚合在当前数据集上把目标查询 P50 降低 99.8153%，说明数仓分层不是装饰，而是在用存储换重复计算。
4. **AI 工程意义**：Agent 不直接访问散乱表，而通过有契约、有限权、带来源的 Tool 获取上下文，为降低幻觉和追责提供基础。
5. **求职意义**：该项目已经能证明候选人横跨数据建模、SQL/Python、批流架构、RAG、Agent Tool、前后端联动与质量治理；若补齐真实运行和测试闭环，可进一步证明生产化能力。

最终定位应保持克制：这是一个**有真实数据、真实查询收益和完整架构演进路径的数据与 AI 工程开发版**，不是已经承载生产 SLA 的成熟数据平台。
